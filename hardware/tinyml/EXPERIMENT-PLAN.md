## 先讀：幾個先前沒想清楚的共通問題

這些是規劃 H0 之後的實驗時發現「原本的計畫沒講清楚」的地方，三個方案都適用，值得在動手前先決定，不要等資料收了才發現設計有洞：

### 1. 樣本數——H0 的「各 3 組」不夠訓練模型

H0 的人工判讀關卡只需要正常/負載各 3 組 run 就能肉眼比對頻譜。但要訓練一個「以 run 為單位分組」的分類器（見 NEXT-SESSION.md 的方法論提醒），3 組正常＋3 組負載切完訓練/驗證後，驗證集可能只剩 1 組 run——一次驗證结果的雜訊會很大，不能代表模型真的穩定。**建議每個類別至少收 8-10 組獨立 run**才夠做出有說服力的 run-grouped train/test split（例如 6-7 組訓練、2-3 組驗證），且每組 run 之間要確實獨立（不同時間、重新啟動馬達、重新施加負載，不是同一次啟動內連續錄好幾段假裝是不同 run）。

### 2. 負載分級——二元 normal/loaded 太粗，但不是免費升級

H0 只需要證明「有負載 vs 沒負載」的頻譜有差異即可。但如果要往「真正的異常偵測」靠攏（呼應 SPA 的異常分級敘事），可以考慮至少三級：`normal` / `light_load`（輕壓）/ `heavy_load`（重壓）。**這不是免費的**——類別一多，每類別需要的樣本數（見上一點）會等比例增加，且相鄰兩級之間的可分性可能沒有 normal vs loaded 那麼乾脆。**建議先把二元分類做穩（A2 過關），有餘裕再擴到三級，不要一開始就挑戰多分類**。

### 3. PWM/佔空比是隱藏的干擾變數

馬達的 PWM 驅動強度本身就會改變振動基準值（佔空比越高，馬達轉速/振動幅度通常越大），如果收資料時 normal run 都用同一個 PWM、loaded run 剛好用了不同 PWM（或反過來），模型學到的可能是「PWM 高低」而不是「有沒有負載」——這是**混淆變數**，不是真的異常訊號。**收資料時 PWM 必須是控制變數**：同一個 PWM 值下收正常/負載成對的 run，如果要驗證模型在不同 PWM 下都穩定，才刻意收多組不同 PWM 的完整正常/負載成對資料，並在訓練時把 PWM 當作已知的分層變數（不要把不同 PWM 的資料混在一起訓練卻假裝它是同一個分布）。

### 4. on-device 部署不能只信 Python 端的準確率

舊專題（`D:\D1\畢業專題`）踩過的坑是：C 轉換器看起來能跑、輸出格式正確，但實際上從沒用到輸入特徵，永遠回傳同一個結果。**教訓是：C 移植完成後，必須拿同一批已擷取的視窗資料，同時餵給 Python 模型與移植後的 C/韌體邏輯，逐筆比對輸出是否一致**，不能只看「編譯成功、能跑」就算數。這件事要寫進每個方案的部署步驟裡，不是事後才想到的驗收項目。

### 5. 展示現場的容錯——live demo 會失敗，要有備案

`live-dashboard/README.md` 自己就提醒了：序列埠被佔用、拔插後斷線不會自動恢復、韌體才剛開機時資料還沒穩定。**正式展示（不管是課程評分還是對外提交）不該把唯一的成功路徑押注在「現場即時連接真硬體且一次成功」上**。建議：
- 展示前至少完整彩排一次全流程（連線→施壓→看到波形變化→分類結果），不要臨場才第一次測試
- 準備一段**錄好的示範影片或截圈的 GIF**作為備案，一旦現場序列埠出狀況，能立刻切換成「這是我們錄好的實測結果」而不是當場卡住
- 若要展示分類結果，準備至少一組「已知會判為異常」與一組「已知會判為正常」的物理操作方式（例如固定用手壓哪個位置、壓多用力），降低現場即興操作導致訊號不如預期乾淨的風險

### 6. 時間現實檢查

寫這份文件時是 2026-08-14 附近，課程截止是 **2026-09-07**，剩下約 3.5 週，且 **H0 都還沒在真實硬體上跑過**。三個方案的工作量遞增很多（方案 C 需要完整機構組裝、多感測器同步、多模態融合），建議的優先序：

- **方案 A 是安全基本盤**：只需要 1 顆馬達 + GY-91，H0 韌體/工具都已就緒，走完 A1-A5 是相對確定能完成的
- **方案 B 是合理的加碼**：INMP441 已有現貨，工作量跟方案 A 同一個量級，但需要額外驗證 I2S 擷取（Arduino 框架下能不能用，或需不需要換 ESP-IDF，是新的未知數，見下方 B0）
- **方案 C 是高風險項目**：需要新機構（伺服加壓臂、干擾馬達）從零組裝、多感測器時間同步、以及全新的融合建模問題（early vs late fusion），**建議當作有餘裕才做的加分項，不要把方案 A/B 沒做完就先動工方案 C**
- 若對外提交賽事有獨立於課程的截止日，這份文件目前沒有追蹤到，需要另外確認，不要假設兩個截止日相同

若時間真的緊張，**方案 A 走到 A4（C 移植 + replay 校驗）就已經是一個完整、可展示、可解釋的 TinyML 故事**，A5（板上即時展示）跟方案 B/C 都是加分而非必要。

## 方案 A（振動）：H0 之後的路線

## 方案 B（聲音）：H0 之後的路線

方案 B 目前**完全沒有程式碼與韌體**，INMP441 已有現貨但沒接線驗證過。跟方案 A 平行，但多一個工程風險：I2S 擷取在 Arduino 框架下的可行性還沒驗證過（NEXT-SESSION.md 提到，若要 I2S DMA 可能需要換 ESP-IDF，但 Arduino 其實也有 I2S 函式庫，能不能用要先試）。

| 階段 | 內容 | 產出/驗收 |
|---|---|---|
| **B0：麥克風接線與擷取驗證** | 接 INMP441（I2S），寫最小可行韌體確認能穩定讀到音訊資料流；**先確認 Arduino 框架下 I2S 夠不夠用**，不夠再評估要不要換 ESP-IDF（換框架等於重寫韌體，是不小的成本，H0 的韌體邏輯不能直接沿用） | 韌體能穩定輸出音訊樣本，格式與取樣率明確定義好（類比 H0 的 JSON 序列協定） |
| **B1：聲音可分性關卡（B0 的姊妹關卡）** | 比照 H0 的精神，收正常/負載各至少 3 組音訊，人工判讀頻譜或能量差異——**這是獨立於 H0 的關卡，不能假設「振動能分，聲音也一定能分」** | 有肉眼可辨差異才繼續；沒有就停，不進模型（跟 H0 同一套判斷邏輯） |
| **B2：資料集擴充** | 同 A1 的樣本數與負載分級考量；額外注意**麥克風固定治具的距離/角度必須跨 run 保持一致**（BOM.md 已標註），否則距離變化本身就是混淆變數 | 每類別至少 8-10 組獨立 run，且有固定的麥克風擺位方式（治具/夾具/量好距離熱熔膠固定） |
| **B3：基準模型訓練** | 音訊特徵通常用頻帶能量、頻譜質心之類的簡化特徵（不必上完整 MFCC，TinyML 資源有限），其餘方法論同 A2（run-grouped 切分、跟人工門檻比較） | 同 A2 |
| **B4：C 移植與 replay 校驗** | 決定特徵是在 host 端算好還是要板上即時算（若要板上即時 FFT，可能需要 ESP-DSP，回頭評估要不要換 ESP-IDF）；同 A4 的逐筆比對要求 | 同 A4 |
| **B5：板上展示驗證** | 同 A5，注意麥克風在展示現場的環境噪音（人聲、其他機器）可能是新的干擾源，建議在 B2 階段就收一些「有背景噪音」的資料做穩健性測試，不要等展示現場才第一次遇到 | 同 A5，額外記錄環境噪音對分類結果的影響 |

## 方案 C（融合）：H0 之後的路線

方案 C 需要方案 A（至少到 A2）與方案 B（至少到 B1）都有基本結果後再開始比較合理，因為融合的前提是「知道各自單一模態長什麼樣子」。零件已按方案 C 需求一次買齊（BOM.md），但機構、接線、韌體整合都還沒動工。

| 階段 | 內容 | 產出/驗收 |
|---|---|---|
| **C0：機構整合測試** | 組裝伺服（MG90S）加壓機構與干擾馬達；驗證**伺服移動到定位後完全靜止才開始錄製**（NEXT-SESSION.md 已警告過的資料洩漏風險：不要學到「伺服在動的嗡嗡聲」）；驗證 MAX98357 警示嗶聲只在推論完成後播放、不與感測擷取視窗重疊 | 一份「機構就緒/施壓中/施壓完成靜止」的明確狀態機（韌體或操作流程層面都可以），錄製時機有明確規則可依循，不是憑感覺 |
| **C1：干擾馬達可分性驗證（方案 C 的核心賣點）** | 收「只有目標馬達」與「目標馬達+干擾馬達同時運轉」兩種情況下的正常/負載資料，比較**加入干擾源後，原本方案 A/B 的分類器/特徵是否還能分辨目標馬達的狀態** | 明確的量化比較：干擾源加入前後的分類準確率變化。如果準確率大幅下降，代表需要專門為多噪聲源情境重新設計特徵或模型，這是方案 C 真正要解決的問題，不是組裝完就自動成立的 |
| **C2：多模態特徵融合** | 決定融合策略：**early fusion**（振動+聲音+電流特徵串成一個向量，餵一個淺層分類器）或 **late fusion**（各模態獨立分類器，再加權/投票）。建議優先 early fusion + 單一決策樹——更貼近「可解釋規則評分」的敘事，也比維護多個分類器簡單 | 一個能吃多模態特徵向量的分類器，同樣用 run-grouped 切分驗證 |
| **C3：Ablation 研究（demo 敘事用，先前完全沒規劃過）** | 用同一批融合資料集，分別訓練「只用振動」「只用聲音」「振動+聲音」「振動+聲音+電流」等不同特徵子集組合，比較各自的分類表現 | 一張「加入越多模態，準確率/穩健性如何變化」的比較表或圖——這是對評審最有說服力的量化證據，證明「多模態融合」不是噱頭而是真的有效，建議直接規劃成展示簡報的一張圖 |
| **C4：板上部署與展示彩排** | 同 A4/A5 的 C 移植、replay 校驗、現場展示要求，但要同時處理多感測器的時間同步（同一個視窗內振動/聲音/電流是否對齊） | 同 A5，額外驗證多感測器資料的時間對齊沒有明顯偏移 |
| **C5（選配，使用者決定）：匯出成 SPA 靜態情境** | 若使用者決定要把真實硬體的異常事件整合進評分用 SPA，做法是匯出成一份新的 `event-XXX.json` 靜態情境檔餵給現有 SPA，**不做即時序列連線，不改動 SPA 的離線架構**（NEXT-SESSION.md 已定調） | 一份符合 SPA 現有情境檔格式的靜態 JSON，且這個決定必須先問過使用者，不是工程判斷可以自己決定的事 |

## 決策檢查點小結

方便快速掃過「現在該做哪一步」：

1. H0 沒在真實硬體跑過 → 先做這件事，其他都先不用想
2. H0 過關 → 進 A1
3. A2 有穩定基準模型 → 可以平行開始 B0（風險評估用，不阻塞 A3/A4）
4. A4 完成（C 移植 replay 校驗過）→ 方案 A 已經是一個完整故事，可以停在這裡展示，也可以繼續 A5 或轉去做 B
5. A 和 B 都至少有 B1 等級的可分性結果 → 才考慮啟動 C0
6. 任何一個方案卡住超過預期時間、且截止日逼近 → 回頭看「時間現實檢查」一節，優先保住方案 A 的完整度，不要三個方案都做一半
